# 3.3.1 OpenAI 元数据与输出上限

## 结论

OpenAI 直接 API 的 GPT-6 Astra、GPT-6 Sol、GPT-6.1 Sol、GPT-6 Luna 与 GPT-6.1 Terra 均支持 1,050,000 上下文、最多 922,000 输入 token 和 128,000 输出 token。pi-ai 1.5.0 的目录曾把这些模型的 `contextWindow` 写为 272,000；272K 只是长上下文计价分界，不是上下文上限。

3.3.1 在插件路由准入中对直接 `openai` provider 使用已核对的元数据，并提供 profile 检查/修复脚本。Codex、ChatGPT Work 与第三方兼容网关保留宿主或供应商报告的容量，因为它们的订阅渠道可能采用更低默认值。

## 真实事件含义

历史会话记录了 `openai/gpt-6.1-sol` 的 `contextWindow=272000`，同时请求实际载入约 368K tokens，随后上游返回 `incomplete/max_output_tokens`。这里有两个不同问题：

1. DSH/pi-ai 目录把 1.05M 的直接 API 模型误报为 272K。
2. 1M context 不代表 1M output；该模型的最大输出仍为 128K。

推理模型的 reasoning tokens 与最终可见文本共同消耗输出预算。达到上限时 DSH 显示“已达到输出 token 上限”是协议层终止原因，不应被解释成 1M 输入上下文失效。

## 检查与修复

只检查，不修改：

```sh
node scripts/repair-openai-metadata.mjs --profile-dir ~/.dsh/profiles/web
```

确认后备份并修复直接 OpenAI provider 中已经存在的模型条目：

```sh
node scripts/repair-openai-metadata.mjs --profile-dir ~/.dsh/profiles/web --apply
systemctl --user restart dsh-web.service
```

`--apply` 只修改 `llm-pi-ai.config.providers.openai.models` 下已知模型的 `contextWindow`，不会新增模型，也不会修改上下文未知的第三方模型、Codex/ChatGPT Work 或其它 provider。修改前会写同目录备份。

## 输出被截断时

- 发送“继续”可以让 DSH 从已有输出继续。
- 长文档、代码库迁移和大表生成应拆成多个有验收边界的步骤。
- `max` 推理会消耗更多输出预算；如果任务不需要最高推理，可降低 reasoning effort。
- 128K 是供应商硬上限，不能通过插件、配置或重试突破。
- 如果输出远低于 128K 仍反复收到 `max_output_tokens`，应保留 Provider、模型、`request/context`、usage 和 provider response id，再判断是渠道上限还是上游异常。
