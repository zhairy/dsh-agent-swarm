# 3.4.0：DSH rc.3 与本机升级

本版以 DSH `0.2.2-rc.3` 为升级目标，保留 rc.1 精确桥接及旧子代理协议。要求 Node.js `>=24.9.0`。不引入新的存储格式、对象库或团队审批真源。

## 子代理与恢复

rc.3 的 `startActivation` 使用顶层 `prompt`、`parent`、`agentOptions`、`agentPreset` 等参数。适配层在创建前通过宿主公开的 `listDescendants` 能力区分协议，不在创建失败后尝试另一个协议，避免重复发布子代理。调用方预留 `childId`，使用 `delivery: caller`，取消和释放仍针对原激活。

历史恢复同时核验 Session header、目录记录及子会话自身的 descriptor。新版目录仅接受 `kind: child`、直接 `parentId` 和 `depth: 1`；孙代、诊断项及名称不能代替直接归属。`turn/end` 只说明回合状态，不能证明后台进程或工作树写者已经停净。

新宿主的结束事件还须匹配该驻留激活的 `runId`、provider、直接父级和 local 标记；旧/重复结束不改变控制状态或消费新等待者。无 runId 的历史宿主保留原路径。

产物的逻辑 workspace 身份固定为根会话，内容从当前任务唯一且经指纹核验的物理目录读取。保留工作树的只读采样不恢复 owner 或写租约；只读专家在首步装配前核验并切到同一产物目录，避免读取源目录却绑定工作树摘要。检查点按 `requestRevision` 隔离无进展历史，旧记录缺省为 1。

规划审核使用独立的在途快照准入，核验根会话、任务、attempt、版本、取消和审核快照，不伪造普通委派记录。审核工具仍只读，合同改版或清理后旧权限失效。

原有 `recovery-required` 工作树、旧 Worker 与租约保持受阻。恢复由新的合法 Worker 显式请求 `swarm_restore_worktree`，不得通过重建工作树、删锁、重放未知工具或改写历史状态绕过。

## 模型与执行桥接

rc.3 原生 `agent/pre-step` 发生在工具和系统提示词装配之后，`agent/request` 禁止改变冻结的选择；这些接口不足以替代同一步失败后的跨模型回退。step bridge 在冻结前选路，在失败且允许重试时重新选择并装配工具与提示词。已执行工具不重放，自动回退不覆盖用户的模型选择事件。

原生 `working-directory/access` 可包围目录访问，但不能在其内部异步检查之后、自动回退提交之前插入复核；文件落盘与子进程启动也没有相同精度的公开钩子。因此继续使用版本及 SHA-256 绑定的物理边界桥接。rc.1 与 rc.3 使用各自的清单，不能混装能力标记或放宽摘要校验。

```bash
node scripts/apply-dsh-step-bridge.mjs --dsh-root /path/to/isolated-dsh
node scripts/apply-dsh-execution-boundary.mjs --dsh /path/to/isolated-dsh/node_modules
node scripts/apply-dsh-step-bridge.mjs --dsh-root /path/to/isolated-dsh --check
node scripts/apply-dsh-execution-boundary.mjs --dsh /path/to/isolated-dsh/node_modules --check
```

对在役安装应用或恢复补丁前，应先停止该安装的全部进程。脚本支持 `--restore`，遇到未知版本、摘要或不可信备份即拒绝修改。

## 升级矩阵

| rc.2 / rc.3 变化 | 本插件处理 |
| --- | --- |
| 具名、多层 Subagent 与 catalog v3 | 顶层启动协议和直接归属恢复；名称仅用于展示和寻址 |
| 生命周期与取消修复 | 保留 caller delivery、原激活 dispose、取消及旧 attempt 围栏 |
| 原生请求重试和继续生成 | 复用宿主重试判定；跨模型选路仍在冻结前完成，不能重放工具 |
| 归档默认清理工作树 | 本机 profile 开启 `worktree.retainOnArchive`；保留分支不能代替保留 ignored 文件 |
| Session 批量 append | 插件未包装/替代 Host append；原有单事件调用继续兼容，EventJournal 不重写 |
| 统一 Team 面板 | 宿主管成员与生命周期，Swarm 管任务合同、权限和证据门禁 |
| MCP 动态注册、代码块 renderer、dsh-doc | 按已有调用核验；不为迁移添加无关功能 |
| 浮层、主题、侧栏 | 检查实际使用的客户端接口，最终以浏览器交互验证 |
| 工具错误分类 | 保留错误与取消诊断，不能将未知副作用当作可重试失败 |
| DeepSeek 会话导入、Windows 更新 | 本次不自动启用实验导入；Linux 部署不声称验证 Windows |

## 验证与回滚

使用隔离 `DSH_HOME`、精确安装包及本地确定性模型完成委派、模型回退、取消、冷恢复、工作树交接和物理执行范围验证。安装包须包含新旧桥接、静态资源与全部运行入口依赖。`SWARM_DSH_MODULES` 应指向本次验证的 patched SDK；系统旧 SDK 不能作为新宿主的回归证据。

```bash
npm run typecheck
npm test
SWARM_DSH_MODULES=/path/to/isolated-dsh/node_modules npx vitest run
SWARM_DSH_VERSION=0.2.2-rc.3 npx vitest run --config vitest.integration.config.ts --maxWorkers=1
node tests/integration/run-execution-boundary.mjs --dsh /path/to/isolated-dsh/node_modules --out /path/to/private-evidence
```

切换前停止全部共享会话存储写者，保存旧程序、profile 和一致数据快照。rc.3 新建子代理会产生 catalog v3，rc.1 无法读取；回滚必须配套恢复升级前的数据代，同时完整保留升级后数据。工作树改动及外部副作用不随数据库快照自动撤销。

本版先完成本机部署和用户验证，再按用户明确授权发布GitHub。第三方兼容资产、安装和回滚见[兼容包说明](3.4.0-第三方插件与兼容包.md)。LayerFS不是运行依赖，未将其当作完整存储架构替换。

## 历史会话与 P6 后续修复

第三方 RigorQuant 的旧 Team API 调用会导致历史 Agent 创建回滚，原生会话释放事件使侧栏条目暂时消失；历史数据仍在，刷新会重建目录。本机兼容版改用同步公共 Team/Subagent 身份，并保留角色权限、原生工具参数、模型路由和关闭态人工选模。订阅额度栏另按宿主指南迁移 CSS anchors，替换已经删除的定位 hook。两者的本地补丁独立记录，不替代第三方上游发行版。

P6 复用整棵图已冻结且不含 Proxy 的分片编码，并在 StateStore 恢复末尾统一物化；不改格式、校验链、逐条验证、fsync 或上下文身份。ext4 热缓存合成状态（约0.5MB、7样本）的50/200增量 EventJournal恢复 p50 从约291/1014ms降至82/254ms，不能外推为真实会话或冷盘保证。单key与noop写入字节保持一致；不同ref的同正文继续分别保留。

上一轮验证包含1737单测通过（14既有跳过）、56 Node测试和57项 Host 集成（确定性模型、0跳过）。其中 runtime-guard 当时仍硬编码旧宿主矩阵，不能把57项全部称为rc.3证据；本轮已补显式rc.3和版本覆盖测试。测量和部署证据留在本机，不包含真实历史正文或凭据的公开记录。


## 连续会话恢复补修

连续委派的线程计划绑定现于启动检查点前持久化，覆盖新建、追加和换线程。对旧版结果提交窗口留下的缺失字段，只有完整身份匹配且仍处于严格恢复围栏的初始线程才补写派生绑定；显式冲突继续拒绝。修复恢复根对话入口，不自动继续旧Worker、重建输入或解除副作用/写租约核验。

已在原始历史副本、精确rc.3 Host、断网且文件系统受限的环境完成安全新回合，使用本地确定性模型，原历史事件前缀保留，工具和子代理启动为0。不将此证据扩大为真实外部供应商或旧任务执行验收。

## 路由和长程等待补修

联网探测为在线仍会进行已配置的有界短重试；短暂故障在链尾硬失败后仍可按健康退避重新探测，继续受总尝试次数、等待预算、半开许可和取消控制。当前历史的 thinking/thought_signature 协议错误不再隔离其他会话的模型。旧健康记录缺少错误原文时仍保持保守隔离，不根据猜测清空。

Google 的额度显示有余量与真实请求429可同时出现；本机小文本探针复现了该行为。Codex的历史TRANSPORT也不能等同于额度耗尽，同模型小文本探针已正常完成。Subscriptions本地兼容版为持久化错误补入白名单传输代码，并去掉账号标识；它没有改变供应商额度、认证或重试分类。

未知等待不能被一句“继续”解除。可靠完成的委派、规划与授权会结算原等待句柄；清理失败或Shell角色缺少可靠停净事实仍保留未知状态。排队完成后的真实投递会重验相关授权；dispose失败进入明确的清理失败结果，不自动启动替代执行。修复轮数耗尽且目标未完成时，检查点返回incomplete。

## 可选 Notebook 接入

本机兼容版将 `@beihaizb/dsh-notebook@0.4.2` 接入现有Host执行边界。算衡等具备计算能力的专家可跨cell、跨模型步骤保留变量；Root只整理草稿。默认只读工作区并禁止网络，`nb_save`仍须当前工作树的精确写scope。Notebook计算与变量探测纳入现有Shell审批策略，不因换一个工具入口而提高权限。

只读内核复用仅限同一委派身份。委派结束或替换身份前等待原进程的真实退出证明；文件sidecar只结算自身进程，不能替整个共享writer epoch解除围栏。所选kernel环境与controller分别挂载，未核验的环境拒绝启动，不能静默换成另一Python。

任务结束后保留有界结果视图（最多64份、合计16MiB的纯JSON快照），停止内核。Host卸载Agent不再把托管Notebook降级为普通会话；结束后的视图只读，未知会话不能启动内核。结果缓存不等于持久文件，服务重启或缓存淘汰前需由获授权的写入流程保存.ipynb。

已有envsel环境未获准计算时仍可读取草稿、结果和可用内核列表。返回的kernel.available/selectionError说明环境状态，不会静默切换用户选择；真实执行继续严格核验环境，其他文件或运行异常仍如实报告。

Python依赖安装在独立环境，精确版本见 `config/notebook-runtime.requirements.txt`，不会安装到系统Python。生产路径通过以下服务环境变量显式配置：

```ini
[Service]
Environment=DSH_NOTEBOOK_CONTROLLER_PYTHON=/path/to/notebook-venv/bin/python
Environment=DSH_NOTEBOOK_CONTROLLER_RUNTIME_PREFIX=/path/to/notebook-venv
```

第三方补丁仅应用于离线副本，版本与文件摘要匹配后才修改。Notebook补丁包含源驱动与编译后的内部桥；它不依赖未公开的Swarm导出路径。Subscriptions补丁保留之前的rc.3界面兼容修改。

```bash
node scripts/apply-plugin-compat.mjs --plugin /path/to/offline-notebook --plan patches/dsh-notebook-0.4.2-rc3-runtime.json
node scripts/apply-plugin-compat.mjs --plugin /path/to/offline-notebook --plan patches/dsh-notebook-0.4.2-rc3-runtime.json --check
node scripts/apply-plugin-compat.mjs --plugin /path/to/offline-subscriptions --plan patches/dsh-subscriptions-0.9.13-rc3-transport.json
```

`--restore`恢复精确原字节；未知版本、混合摘要或路径越界直接拒绝。不要对正在使用的插件目录运行应用或恢复操作。

JS/TS使用已有受管bash与Node24，浏览器使用agent-browser独立session；不引入新的console REPL、跨任务活变量恢复、多语言预热池或microVM平台。完整限制和后续阶段见[已知问题与迭代计划](3.4.0-已知问题与迭代计划.md)，公开验证摘要与补丁包随v3.4.0发布。
