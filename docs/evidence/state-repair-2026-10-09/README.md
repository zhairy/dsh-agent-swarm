实际 `persistence.enabled=false`，故不能直接重启丢掉内存任务。维护过程先在隔离 DSH 证明合法 HMR 加载/移除单一受信维护插件不会重载原服务，然后只导出编排状态：最后合法副本与当前 owner 的任务、委派、线程、上下文、预算、控制、健康分开保存。Node 本进程诊断不开放网络调试端口；临时入口已移除，profile 与配置哈希完全恢复。原始私有数据没有加入仓库。

离线修复只恢复逐字可证明的历史流程号：D-1/D-2 除 workflowRevision 外与最后合法记录相同，原始结构化结果哈希不变。保留当前 T-1 的 2/4/1，未伪造规划批准；只撤销确定未开始的单个预约。修复后完整严格校验通过，见 [脱敏修复记录](root-cause-and-repair.json)。

一次性交接仅接收固定私有路径下经维护明确暂存的 2.3.0 状态；同 UID、0700/0600、普通文件、版本/作用域/哈希/结构和容量均检查。初始化与身份恢复成功后才消费，失败保留原件；不启用持久化、不提供 Agent 读私有状态的新接口。state/ledger/maintenance 三个目录由同一个私有根清单保护，消费后的副本也一样。

## 四类附带报错

- `offset 130` 超过 README 当前 93 行：失效行号，先从第 1 行按总行数分段读取，不猜旧位置。
- `taskView` HTTP 401：公开的是 API 契约，访问仍需宿主认证；模型优先使用授权的 `swarm_status` / `swarm_context_read`，不匿名 curl 或取登录凭据。
- `agent-browser screenshot --path ...`：当前 CLI 的图片路径是位置参数，正确形式 `agent-browser --session <session> screenshot <path> --json`。
- `jev_check` 缺 propositions：`state` 和 `propositions` 必须顶级并列，嵌在 state 内会在调用模型前被拒绝，不是 Jev 审核否定。

已修正说明、模板和诊断，不弱化 HTTP 鉴权、私有读取守卫或规划门禁。
