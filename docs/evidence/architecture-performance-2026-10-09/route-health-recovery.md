# 跨根路由健康恢复：成功事实不能被旧快照撤销

## 根因和反例

2.3.1 的隔离恢复只合并“失败记录”。真实 half-open 请求成功后，运行内存删除对应隔离项，却没有持久保存“这次失败已经恢复”的事实。此后打开另一个旧根会话，它的失败快照再次 `RestoreHealth`；由于当前 Map 中该项不存在，旧失败重新进入共享 Map，恢复过的首选模型又被隔离。

使用强制提前探针最容易区分此问题和正常冷却：记录 pool 失败并保存根 A 的旧快照；在插件冷却到期之前，用户强制单 owner 探针，真实调用成功；再恢复根 B 的旧快照。旧代码重装未来冷却，新代码保留恢复事实。该测试只使用合成健康状态，不实际调用订阅模型。

## 持久事实和合并规则

保留旧 `list/getHealth` 数组作为诊断展示；新增稳定快照：

```ts
{
  schemaVersion: 1,
  entries: RouteHealthEntry[],
  cleared: Array<{ key: string; failedAt: number; failureId?: string; clearedAt: number }>
}
```

每个新失败拥有 UUID。`failedAt` 对实际关联的资源 key/aliases 单调递增，解决同一毫秒发生“恢复→新失败”的歧义；这是因果排序，供应商 `resetAt` 仍是独立的明确额度恢复下限。插件 `retryAt` 使用真实时钟计算冷却。

成功仅清除确实由该 owner claim 且未越过 provider reset 的隔离项，并为它当时的全部实际 aliases 写入清除事实。合并旧状态时，只有该资源同次/更旧失败被抑制；其他账户、域、池和之后的新失败仍保留。无身份的 legacy 数组仍可恢复，按已有失败时刻进行保守比较。

`clear` 也记录清除事实，未来 provider reset 不可由普通 clear 或 force 绕过。恢复的清除事实若早于已知 `resetAt`，不能拿它消除该隔离。运行中的 half-open owner 不进入稳定快照，较旧失败恢复不能覆盖当前 owner。

快照和墓碑先整体验证、核对容量，再原子合并。`validateRouteHealthSnapshot` 同时供 FeatureState 边界和注册表使用，避免两个版本的校验规则再次漂移。调用链还须在成功后提交稳定快照，并在下一次模型派发前确认所需持久化完成；这部分由 route-state/runtime 接线实现和测试。

## 空间取舍和故障反馈

entry、alias 和清除事实共用最多 **4,096 个不同资源 key**。一个资源后续失败/恢复复用该身份，不按执行轮次永久新增墓碑。清除事实不采用 TTL 或 LRU 淘汰：旧根可以很久以后才加载，遗忘墓碑会重新引入旧失败。

达到身份容量时，新增资源被拒绝，返回受控诊断 `route-health-capacity-recovery-required`，原快照保持不变；现有身份仍可记录失败和恢复。此机制没有默默删除恢复事实。应在宿主维护流程中核实旧根快照已迁移/退役后再进行显式状态归档，不能建议用户重试或子 agent 直接编辑私有状态。

空间复杂度为 O(K + 关联路由元数据)，K≤4,096；key 长度仍有上限。整个 FeatureState 另受原有 4 MiB 上限约束，资源 key 数量限制不代表可以绕过总字节容量。稳定快照按根持久化会重复同一共享健康事实，是现有架构的空间成本；本轮没有引入独立全局数据库迁移。

按资源查询/claim 只检查该路由的少量关联 key；成功清除和快照生成扫描当前 key。恢复还包含 aliases 的去重与重建，最大关联量受上述容量约束，不能宣称所有路径都是 O(1)。

## 验收

route-health 定向 **25 项**通过；route-health、route-state 和 FeatureState 校验联跑 **88 项**通过。新增回归覆盖：

- 强制提前成功后，旧 modern/legacy 根快照均不能重新隔离。
- 进程重启和根加载先后顺序改变，仍保留恢复事实。
- 同毫秒真实新失败、后到的新失败快照不被旧成功吞掉。
- quota domain/pool 的 aliases 一致恢复，其他账户继续隔离。
- provider reset、owner 身份和 live claim 边界继续成立。
- 墓碑格式错误、容量拒绝不发生部分改写；满容量下现有资源仍能恢复。

上述结果证明合成状态机和持久边界行为，真实宿主重启、模型调用与全项目验证由总审核另外记录。
