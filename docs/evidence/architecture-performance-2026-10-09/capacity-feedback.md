# 长任务资源边界：反方结论及恢复反馈设计

以下复现使用临时工作区、假数据和既有 2.3.1 编译模块；不读取生产私有状态，不调用真实模型。资源拒绝本身是保护机制，不能据此删除历史、放松校验或直接提高上限。

## 容量与恢复是不同问题

| 边界 | 可证实行为 | 影响与建议 |
| --- | --- | --- |
| 全量任务状态默认 4 MiB，内存模式也生效 | 合成每条 64 KiB summary 的合法失败委派，63 次提交成功，第 64 条加入内存后提交得到 `STATE_TOO_LARGE`；后续任意全量提交重复失败；运行态有 64 条、已提交态 63 条 | 容量失败必须指明运行态和已提交态的差异，禁止声称重试或普通重启能保留全部工作。应在产品化归档前提供可执行的分任务/新会话建议，并设计完成记录入账失败的事务回收或独立受审归档；不能静默删除已执行原始结果 |
| 上下文默认 512 项 | 同修订每次委派新增 L2，合同改版仅回收本任务旧版本材料 | 当前默认 legacy 执行次数没有限制，不能假设 maxCalls 会先阻止到达此边界。容量检查应尽量早，错误需包含安全数量信息；不要用无版本的 LRU 淘汰破坏任务 ref、评分映射及盲审范围 |
| P2P 默认最多保留 2,048 封 | 缩小容量为 2：第一封已 ACK，第二封 TTL 已过，pull 无可交付消息，第三封仍 `MESSAGE_LIMIT`；公开方法只有 send/pull/ack | ACK 和 TTL 只改变可交付性，不等于归档，也不会恢复 retained 容量。旧报错“archive before sending”没有对应公开操作，必须改为真实的恢复指引。本轮不新增归档能力 |
| 文件摘要默认最多 256 个文件 | 合成 1,001 个空目录，`maxFiles:1` 仍遍历全部目录，输出 0 项、complete=true，一次约 96 ms | maxFiles 只约束文件结果，不能声称目录遍历时间/空间已经有界。后续可用 opendir、访问条目/目录和深度上限、取消检查；达到访问界限必须输出 unknown、complete=false，不可伪装完整摘要 |

状态增长案例仅证明可达的资源边界与运行态/提交态差异，不证明当前生产会话已达到 4 MiB，也不把所有容量失败等同于 2.3.1 已修复的修订一致性故障。

## 反馈约定

建议固定错误码区分 `MESSAGE_LIMIT`、`STATE_TOO_LARGE`、状态不一致、权限拒绝、取消、临时供应商故障。提示包括受控的资源类别、当前量/上限、操作是否启动、是否已提交、哪些原始结果仍保留以及下一步。禁止输出私有状态内容、凭据、原始对话或未经脱敏的第三方错误正文。

P2P retained 满时应明确：已 ACK/过期消息仍计入保留容量；继续 pull/ack 或重试 send 不会释放容量；当前没有公开归档工具。可以在宿主指导下保留原会话，在新根任务会话建立新邮箱，必要材料通过已有授权引用/正常委派重新建立身份；不能让子 agent 读取或编辑私有状态文件。持久化关闭时普通重启会丢失内存状态，不能将重启作为无损恢复建议。

未来归档必须包含引用闭包：task→delegations/contexts、contextDelegations→evidenceAssessment、message/ACK→bindingHistory、experience→原任务/审核/产物证据。归档先固化并验证，再在同一 CAS 事务移除活动索引；取消/并发、恢复重放和旧 ref 不越权必须有回归。只删最大对象或改成“校验忽略旧记录”会恢复写入表象，却破坏可信交付链。

## 正反交叉审核

反方支持正方按需计算执行预算：无限制普通调用与豁免 Jev 无需扫描完整历史；启用限制时保留原有 reservation 及真实/未知用量的计费规则。本轮不增加容易与取消、重启和迟到用量漂移的聚合缓存。

反方独立核对并认可正方的最终派发竞态：旧合同通过门禁后，等待产物摘要期间合同改版，delegator 重新读取新合同并创建新版本的 child binding，现有工具守卫会允许该新绑定。最终把结果标为 stale 只阻止验收，不能撤销已经启动的模型或副作用。修复必须在真正 start/send/native 派发末端验证原始 admission，并覆盖异步预检后的竞态；不能仅在入口或结果回填时检查。

应优先验证正确性边界，再优化有重复扫描证据的热点。全量提交 O(S)、完整验证和崩溃恢复语义仍需保留；不能用吞错、缓存授权或放宽校验换取表面速度。
