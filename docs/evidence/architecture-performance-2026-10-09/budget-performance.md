# 执行预算路径的性能审计

审计基线：2.3.1，Git `e38b0a6fc6ebc20336f70a522b76b7a8af88e7d1`。本节覆盖 `createExecutionBudget.reserve/start/settle` 的同步控制开销；不加载插件入口，不构建或改写生产 `lib/`，不调用真实模型，不读取业务会话。

## 已确认问题与实现

旧实现每次预约先复制、筛选全部历史预约，再计算次数、token 和费用，即使相关上限全部为 `0`（不限）。因此，累计执行 N 次预约时，历史扫描总量为 Θ(N²)，临时数组最坏为 O(N)。Jev 原本不受这些限额约束，但仍先执行一次没有用途的历史扫描。

本次保留同一个预算模块和恢复 schema，只在对应正限额启用时读取历史并计算所需指标。Jev 在进入历史扫描之前跳过限制检查，继续保留使用量观测。不限额的生成预约、Jev 预约均为摊销 O(1)；启用次数、token、费用或数学工作量限额的对应路径仍为 O(N)。预约记录仍完整保留，空间仍为 O(N)，快照导出仍为 O(N)，没有宣称减少持久历史占用。

保留的语义包括：相同 ID 的幂等与冲突判定；仅未发送的预约可退还；已发送及恢复后未知用量继续计费；延迟用量补记；数学与生成计数隔离；正 token/费用上限对未知估算保持拒绝；次数、token、费用、覆盖度错误的原有优先顺序。没有增加 Jev 调用次数、费用、并发或速率限制。

## 交叉评审与验证

反方专家对上述分支和错误顺序进行独立检查，未发现语义回归。定向预算单测 11 项通过；新增的行为用例先在无限额度下保留真实发送、取消、数学和 Jev 记录，再恢复并启用各类正限额，验证历史依然被正确计入，Jev 仍然豁免。该用例验证恢复后的资源合同，不依赖本次优化的分支实现。

另增加 `getReservation(id)`，直接查询并复制一条预约，供计算请求查重及状态核对使用，避免仅查询一个 ID 却复制全部历史。读取结果不能修改内部预约或嵌套 usage；恢复后的延迟用量更新仍可见，单测已覆盖。这项查询对预约历史数量为 O(1)，完整快照接口与恢复 schema 不变。

可复现基准脚本为 `scripts/bench-budget.mjs`。脚本对传入的可信源文件在隔离 Node 进程中转译并导入，不生成 `lib/`，不启动 DSH、服务、shell 子 agent 或网络请求。每个规模预热 5 次、采样 30 次，统计完整 N 次 reserve/start/settle 批次；快照导出与 GC 均不计入批次耗时。

环境为 Node 24.21.0、Intel Core Ultra 5 125H、Debian Linux 6.12.107。原始数值和源文件 SHA-256 保存在 [budget-benchmark.json](./budget-benchmark.json)。该记录是本地合成控制面基准，不代表端到端模型延迟、token 或费用节省；后台其他审计工作和运行时调度仍可能造成噪声。

N=5,000 不限额生成批次的 p95 为 1,658.092→87.605 ms；Jev 批次为 330.841→87.461 ms。正次数限额路径仍需遍历历史，增长趋势仍接近二次，不能把此次短路优化描述成所有预算操作都是常数时间。

同一规模的快照字节数前后完全相同。例如 5,000 次不限额生成均为 1,019,156 bytes，Jev 均为 989,142 bytes。5,000 次不限额生成的 GC 后活跃预算 heap 增量中位数为 1,048,624→1,052,248 bytes；整个基准 worker 的 peak RSS 为 230,502,400→230,223,872 bytes。这些数值支持“历史未丢失、空间仍为 O(N)”；微小差异不作为内存节省或回归结论。Heap 增量不是峰值分配，worker RSS 包含 Node、转译和全部基准场景。

## 性能边界

完整任务状态持久化、任务状态输出仍需导出和校验完整预约历史。因此，这项优化直接消除了预约入口的无效扫描，但不能单独保证整个委派链变为 O(1)。`feature-session.budgetFor` 可缓存固定大小的当前限额签名，仅在配置发生实际变化时获取完整快照并执行原有转换保护；这与删减历史或缓存实际用量不同。审计不建议在本轮引入容易因取消、延迟用量及恢复而漂移的累计用量缓存。
