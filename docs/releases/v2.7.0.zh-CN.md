## ✨ 新增功能

- **按段快照**：快照从单个 `snapshot.json` 改为 `snapshot/` 目录，段文件按内容指纹命名并复用——一代快照只重写发生变化的段，未变段直接沿用上一次的文件；`meta.json` 最后原子替换，读取优先按段快照、缺失时回退旧的整份快照。
- **布局版本与指纹**：日志行与快照同时记录布局版本号与布局指纹。低版本目录会在下一次写入时自动补一条迁移全量行，之后继续写增量行；目录版本比代码新时直接拒绝打开，避免旧代码改写新目录。
- **孤儿委派修复命令**：`npm run repair:state -- <状态目录> [--dry-run]`。增量路径仍然在校验层显式拒绝「任务索引与委派记录不一致」的状态，这条命令是它对应的出口：删除所属任务已不存在的委派、按记录重建任务索引，先在内存里通过完整校验才写回。
- **发布流程自动化与模块清单校验**：`npm run pack:release` 先构建，再按 `lib/index.js` 的依赖闭包逐项核对 `npm pack` 清单，缺文件立即失败；通过后才产出 tarball 与 `SHA256SUMS`。

## 🎨 体验优化

- **委派按任务分桶**：`delegations` 段的分片数从「委派总数」降为「任务数」，长任务的段内分片数不再随历史线性增长；整份状态编码与扁平布局逐字节一致。
- **绑定历史有界归档**：主状态里每个 agentId 只保留最近 4 条历史绑定，更老的先写入 `history/bindings.jsonl` 再从状态移除，主状态分片数因此有界。归档先于删除，崩溃只会留下可去重的重复，不会丢审计记录。
- **全量提交常数回归基本消解**：实测 0.25/1/4/8/16 MiB 状态的全量 `commit` 相对 2.6.0 为 1.13×/1.25×/1.04×/0.97×/1.05×；增量提交保持 0.15–0.22 ms 且与规模无关。

## ⚠️ 其他变更

- 旧整份 `snapshot.json` 仍可读取；写入侧改为按段快照后不再生成整份文件。
- 2.6.0 的日志行把布局哈希写在 `layout` 字段里，本轮按旧算法复算比对，仍可完整恢复。
- 曾尝试「从整份编码切出段/元素子串以避免二次编码」，实测反而更慢（JS 逐字符扫描慢于原生 `JSON.stringify`），该实现与测试已删除；本轮真正的收益来自段哈希缓存与分桶。
- 绑定历史归档文件不参与恢复：被移出主状态的历史绑定不再能通过 `bindingHistory` 查询，消息校验对超期绑定按 fail-closed 处理。

## ⚠️ 已知边界

- 修复命令只处理孤儿委派与委派索引两类结构问题；其它字段损坏仍由完整校验拒绝，需要人工处理。
- 依赖闭包校验只识别相对 `.js` 字符串字面量，动态拼接路径与非 JS 资源不在覆盖范围内。
- 快照目录与 journal 仍在同一状态目录下；进程级崩溃不会产生半个代次，断电级损坏仍需人工判断。
- 基准为开发机内存态测量，不是 NAS、端到端、LLM 成本或 Token 收益基准。
