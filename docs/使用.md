# 使用

## 天枢怎么工作

在「天枢」会话里，你只需用自然语言描述目标和验收条件。天枢按固定协议推进：

1. **建立任务卡**（`swarm_task_card`）：记录目标、验收标准、范围、风险标志和性能预算（不知道的写「待测」），生成 Mermaid，并对目标、流程设计、代码分别进行生成后审核。规则引擎据此给出**硬门槛**；衡鉴（Jev）在规则未覆盖的部分补充门禁，**只能增加、不能减少**。
2. **委派专家**（`swarm_delegate`）：把自包含的子任务交给某个角色。插件负责选择模型路由、限制工具权限、校验结构化交付，并把证据写入账本。交付完成后，衡鉴调用 Jev 做**复评**：结论是否有依据、回应是否完整、角色专项要求是否达到，给出「可信 / 需核实 / 存疑」和可信度，写在委派结果里（详见 [角色.md](角色.md#衡鉴复评)）。
3. **查看状态**（`swarm_status`）：查看每个门禁是否已由证据满足，以及各委派的路由、耗时和告警。
4. **验收**（`swarm_accept`）：`accept` 时逐项核对门禁证据，缺一项就返回 `blocked` 和缺失清单；`reject` 进入修复轮次，最多 2 轮；`incomplete` 如实记录未完成的部分。`accept` 时衡鉴还会复评验收结论本身；复评只作提示，不改变验收结果。

不同风险的任务会拉起不同规模的角色组合：

| 任务 | 典型角色组合 |
|---|---|
| 微小低风险改动 | 疾风 + 复核 |
| 一般代码任务 | 铸剑或疾风 + 复核 |
| 架构、并发、算法 | 另加御史 |
| 交易/量化核心 | 另加算衡研算与验算、差分/性质测试 |

另外三个角色按需出场：行舟只在有明确执行步骤时，观象只在有图片时，妙笔只在需要文案时。

## 模型显示

百工会话（天枢、角色预设以及委派出的专家会话）里：

- 每次调用模型，聊天窗口都显示一行「调用模型：模型 · 供应商（路由名）· 推理强度」，例如 `claude-opus-5-5 · Claude 订阅（claude） · 推理 max`；同一轮里因回退、容灾升级或手动切换换了模型时，显示「切换模型」并注明原来的模型。这一行属于本轮的过程区，轮次结束后随过程一起折叠。觉得太密时，可在「设置 → 百工 Agent → 专家会话与重试」把「聊天中显示调用模型」改为「每轮首次与换模型时显示」（`agents.modelCallDisplay: turn`）。
- 会话头部显示最近一次请求实际使用的模型与供应商。
- `swarm_delegate` 的结果写明专家使用的模型、供应商与提示风格，例如 `模型 gpt-6-sol · ChatGPT 订阅（codex） · 推理 xhigh · GPT 风格（目标/停止条件/证据）`。

显示只读取 DSH 已经记录的会话事件（`assistant/message` 的来源、`request/header` 的推理强度），不写入自定义事件，卸载插件后会话记录不受影响。

## 按模型家族组织提示

不同模型家族对提示的偏好不同（参考 oh-my-openagent 的 agent-model-matching、Anthropic 与 OpenAI 的官方提示指南），插件按路由自动选择：

| 模型 | 专家 persona 与任务说明 | 天枢追加的调度说明 |
|---|---|---|
| Claude（Opus / Sonnet） | XML 分节（`<role>`、`<boundaries>`、`<task_context>`、`<task>`、`<deliverable>`），长材料在前、要求在后，写明约束的理由，报告简洁、不重复自检 | 委派说明用 XML 分节；只把独立工作并行委派 |
| GPT（Codex：GPT-6 Sol / Astra 等） | Role / Goal / Success criteria / Constraints / Output / Stop rules；任务说明为 GOAL / CONTEXT / STOP WHEN / EVIDENCE / DELIVERABLE；偏向直接行动 | 每个委派写清 GOAL、STOP WHEN、EVIDENCE |
| 其他（DeepSeek、Qwen、Kimi、GLM、MiMo、MiniMax 等） | 编号的必做项、成功标准与停止条件 | 编号的调度步骤 |

专家的风格按**实际启动的那一层路由**决定（首选模型启动失败、退到下一层时，persona 与任务说明一起换成新模型的风格）；连续会话沿用建会话时的风格。原生 Codex 后端用 GPT 风格，原生 Claude Code 用 Claude 风格。也可以在「设置 → 百工 Agent → 专家会话与重试」把「提示风格」固定为某一种（`agents.promptStyle`）。

## Jev 判断工具

天枢以及谋定、枢机、算衡、博闻、御史、复核可以直接调用 7 个内嵌的 Jev 工具，做快速、可复核的类型化判断（单次约 0.3–3.5 秒、约 $0.00001，不设额度）：

| 工具 | 用途 |
|---|---|
| `jev_check` | 一组独立的是/否检查，例如逐条核对验收标准是否被交付满足（≥0.7 进 flags，0.3–0.7 进 uncertain） |
| `jev_classify` | 从封闭标签集合中选一个（默认加 other；ensemble 时打乱顺序复判） |
| `jev_score` | 按有序档位打分（风险、完成度） |
| `jev_match` | 在候选中找真正的匹配，并给出「确实存在匹配」的概率（去重、对齐） |
| `jev_screen` | 处理网页、文件等不可信文本前，筛查提示注入信号（pass / review / block） |
| `jev_ask` | 自定义 noul / choice / score 题目 |
| `jev_health` | 检查 Jev 是否可用（不计费） |

用法写在随插件发布的技能 `jev-judgments`（中文）与 `typesafe-ai`（官方说明）里。工具语义与 jev-mcp v0.2.1 一致，但由插件直接调用 TypeSafe，与衡鉴共用客户端和凭据；Jev 所有入口不设本地限流或使用额度（旧 `jev.maxRequestsPerSecond` 配置被忽略），不需要外部 MCP 进程。

**API key**：在「设置 → 百工 Agent」顶部的「Jev 模型 API Key」卡片里粘贴保存（存入 DSH 凭据存储，引用名默认 `TYPESAFE_API_KEY`，不会显示，也不会写入配置文件），保存后新的 Jev 调用立即使用；「测试连接」会列出账号可用的 Jev 模型。如果密钥由环境变量或服务环境文件提供（例如 systemd 的 `EnvironmentFile`），卡片显示「只读」，需要在环境里修改并重启 DSH。

## 网络中断与回退恢复

模型请求因传输失败、超时或订阅令牌无法刷新而出错时，插件先探测网络（`agents.networkProbeUrls`，任一地址有 HTTP 响应即视为联网）：

- **断网**：不再把整条路由链依次耗尽，而是等待网络恢复（最长 `agents.networkWaitMs`，默认 10 分钟），恢复后在原模型上重试；同一会话 30 分钟内最多等待 3 次。专家的自动重试同样先等网络。
- **联网**（只是某个供应商故障）：照常按路由链回退。
- 天枢回退到备用模型后，经过 `agents.rootRecoverMs`（默认 10 分钟）会重新尝试对话框所选的模型，不会一直停在兜底模型上。

委派失败时，错误后面会附中文说明，例如 `error：DeepSeek Messages transport failed（说明：网络连接失败：无法连到模型服务……）`。

## 门禁（硬门槛）

| 门禁 | 什么时候必需 | 什么证据算满足 |
|---|---|---|
| `G_VERIFY` 复核 | 任务涉及代码改动；或出现过铸剑/疾风的委派；或天枢自己改过文件 | 最后一次编辑**之后开始**的复核判定为 `pass`，且至少一条命令带退出码；这期间**任何一次**复核判定为 `fail` 都会否决 |
| `G_REVIEW` 御史 | 跨模块架构、共享状态并发、算法改动、安全、资金逻辑、时间序列/回测；或 Jev 判定变化较大 | 最后一次编辑之后的**全部**御史审查中，每条 critical/high 发现都在 `swarm_accept` 的 `findingResolutions` 里写明了处理结果 |
| `G_MATH_RESEARCH` 算衡·研算 | 改变算法语义；或 Jev 判定为 research | 研算结果包含不变量和复杂度 |
| `G_MATH_VERIFY` 算衡·验算 | 资金、时间序列/回测、状态机、数值精度、共享状态并发；或 Jev 升级 | 最后一次编辑之后的验算：每个反例（`refuted`）都在 `findingResolutions` 中说明了处理，且最新一次验算至少证实（`proved`）一条结论；与研算模型家族相同时标注「独立性未实现」 |
| `G_DIFF_TEST` | 资金或时间序列类的算法改动 | 复核结果中有通过的 `differential` 或 `property` 类命令，且没有失败的同类命令 |
| `G_BENCH` | 声明了性能预算（「待测」不算）；或 Jev 判定需要基准测试 | 复核结果中有通过、且摘要带数值的 `benchmark` 类命令，且没有失败的基准命令 |
| `G_VISION` | 任务包含截图、设计稿或视觉产物 | 观象完成了观察（不是 blocked） |

两个模型都认为没问题，不算通过。复核的结论必须来自真实运行的命令和退出码。

「最后一次编辑」的计算范围：

- 铸剑、疾风完成的委派；
- 已经启动、失败了但确实改了文件（或改动无法追踪）的编辑委派；
- 天枢在任务创建之后自己调用 `write`/`edit` 的时刻。

天枢通过 shell 写文件无法识别，这是已知限制。

## 直接使用角色预设

新建会话时可以直接选择角色预设：

- **算衡**：只做数学研讨；
- **妙笔**：只写文案；
- **复核**：只运行检查并解释失败，不修改业务代码。

在这些预设中，只读类角色调用 `write`/`edit` 会被守卫拒绝，也没有 shell。

## 专家会话与自动重试

**一次性调用还是连续会话，由衡鉴判断。** 每次 `swarm_delegate` 之前，衡鉴（Jev）根据任务目标、本次请求和该角色已有的会话回答两个问题：

- 这位专家在同一大类任务里还会不会被再次调用（按审查意见修改、复查、补充验证、继续深入）？会 → 开**连续会话**（DSH 的 continuable 子会话）；不会 → **一次性调用**。
- 已有同角色会话时：新请求是否与它此前的工作同一大类？是 → **追加**到该会话，专家保留已读过的文件与已有结论；否 → 开新的连续会话。

算衡的研算与验算各用各的会话，验算永远看不到研算的上下文。并行委派时，正在工作的会话不接受追加，会另开会话。Jev 不可用时按规则：同一任务已有该角色的会话就追加；铸剑、疾风、行舟、复核、御史开连续会话；其余一次性。天枢也可以在 `swarm_delegate` 里用 `session` 指定：`continue`（追加到最近的空闲会话）、`new`、`oneshot`。连续会话在 Web 界面里和普通子会话一样可以打开查看，也可以直接在里面追加消息。

**自动重试。** 专家没能执行（会话建立失败、投递失败）、执行中断或出错、没有提交结构化结果或结果不符合契约时，系统自动处理，默认最多 3 次（`agents.maxRetries`）：

| 情况 | 连续会话 | 一次性调用 |
|---|---|---|
| 执行出错（例如整条路由链暂时不可用） | 等待 5 秒起、逐次加倍后，在同一会话里从主模型重新续跑 | 等待后重新启动 |
| 执行中断、输出过长被截断 | 在同一会话里「从中断处继续」 | 重新启动 |
| 没有 json / 结构化结果不合格 | 在同一会话里只要求修正结果，不重做已完成的工作 | 重新启动并附上失败原因 |
| 会话建立或追加投递失败 | 换一个新的连续会话重试；多次失败后改为一次性调用 | — |
| 暂时没有可用路由 | 等待后重新检查 | 同左 |

会话策略（由衡鉴判断 / 全部连续会话 / 全部一次性）、两个判断阈值、重试次数、首次等待时间、提示风格、断网等待与天枢恢复时间都可以在「设置 → 百工 Agent」的「专家会话与重试」里修改，保存后新的委派立即生效（写入 swarm-core 的 `agents`）。天枢或用户取消、模型明确拒绝时不重试。**专家执行不设时间限制**，也不按次数限制同一专家的调用（`budgets` 默认 0 = 不限）。连续会话的结果由 `swarm_delegate` 直接返回，DSH 随后投给天枢的「子智能体已结束」通知会被滤掉，同一结果不会进天枢上下文两次。

## 账本

每个会话一个 JSONL 文件，路径为 `%USERPROFILE%\.dsh\share\dsh-agent-swarm\ledger\<会话 ID>.jsonl`。事件类型包括：

- `task/card`
- `delegation/queued` / `running` / `completed` / `failed` / `blocked`
- `route/skipped`、`route/fallback`
- `jev/call`、`native/call`、`accept/decision`
- `route/upgrade`（容灾升级）、`review/assessment`（衡鉴复评）
- `session/plan`（会话方式：一次性 / 新建连续会话 / 追加）、`delegation/retry`（自动重试）

写入前会脱敏，不记录密钥、完整 prompt 或源码。`swarm_status` 会给出当前会话账本的路径。

## 覆盖路由与策略

在 profile 的 `cordis.patch.yml`（例如 `%USERPROFILE%\.dsh\profiles\swarm\cordis.patch.yml`）末尾追加对 `swarm-core` 行的覆盖，然后重启 `dsh`。可参考 [config/roles.example.yaml](../config/roles.example.yaml) 和 [config/policy.example.yaml](../config/policy.example.yaml)。

注意：

- 覆盖会**整体替换** swarm-core 的 config，没写的字段会恢复默认值。
- 各角色的模型路由可以直接在 Web 端「设置 → 百工 Agent」里配置（默认 4 层：主模型 → 备用 1 → 备用 2 → 兜底，可增删层；每层先选供应商、再选模型与推理强度；可升级的角色另有「容灾升级」），保存后写入 swarm-core 的 `routes`，新委派即时生效。页面顶部的「专家会话与重试」写入 `agents`。其余字段（预算、Jev、衡鉴复评 `review`、原生后端等）仍按本节方式在 `cordis.patch.yml` 覆盖；配置字段都标记为 volatile，每次读取都取最新值。

## 常见阻塞

| 返回 | 含义 | 处理 |
|---|---|---|
| `vision-unsupported` | 观象的路由链上没有支持图片输入的可用模型 | 在「设置 → 模型」启用支持图片的模型（例如 qwen3.8-max），或覆盖 `guan_xiang` 的链 |
| `no-usable-route` | 链上的 provider 都没有配置或无法解析 | 运行 `npm run doctor`，补齐 provider 与 key |
| `native-unavailable` | 请求了 codex/claude，但对应官方 bundle 未安装 | 按安装文档第 7 步安装；插件会自动退回 API 路由 |
| `native-budget` | 本会话的原生后端调用次数已用完 | 调大 `native.maxCallsPerSession`，或直接用 API 路由 |
| `rules+jev-fallback` | Jev 超时、限流或未配置 key | 这是保守结果：涉及算法改动时会强制验算与审查 |
| 衡鉴复评：存疑 | Jev 认为交付的结论缺少依据或不完整 | 核实该交付的证据，或重新委派（配置了升级的角色会自动换升级模型） |
| 衡鉴复评：未执行 | Jev 关闭、缺少 key，或多次重试后仍失败（复评不设额度） | 委派结果照常可用；需要复评时补 key 或检查网络 |
| 预算上限 | 在 `budgets` 里设置了非 0 的委派次数上限（默认不限） | 拆分任务，或调大/清零 `budgets` |
| 自动重试 N 次 | 专家未执行、中断、出错或交付不合格，系统已自动续跑或重启 | 通常无需处理；重试用尽仍失败时看「错误」与路由记录 |
| `DeepSeek Messages transport failed` 等传输失败 | 连不上模型服务；多为本机断网或代理异常，整条路由链都会失败 | 插件会等待网络恢复后重试；长时间断网时检查网络与代理，恢复后在会话里发送「继续」 |
| `jev_*` 返回 401 | 没有配置 Jev API key | 在「设置 → 百工 Agent」顶部填写并测试连接 |
| `State schema validation failed` / `STATE_INVALID` | 插件拒绝写入不符合状态约束的快照，可能影响多个写入工具 | 保存错误及 `swarm_status` 中的版本和诊断，交由维护者定位；不要反复重提同义任务卡、读取或修改私有状态。重启后仍须重新确认写入和规划审核有效 |
| `read: offset … is out of range … (N lines)` | 请求行号超过当前文件长度，常见于沿用旧版本行号 | `offset` 是从 1 开始的行号。从文件开头或当前检索命中处重新读取，引用本次实际读取的行号 |
| `/api/swarm.taskView` 返回 401 | Web 请求未通过 DSH 宿主认证；只读接口也受认证保护 | 会话内优先用 `swarm_status` 与 `swarm_context_read`；界面通过已登录的宿主连接访问，不关闭认证或把登录凭据写入命令/文档 |
| `jev_check: $.propositions 缺失` | 命题表未放在工具顶级参数中 | 把 `propositions` 移到与 `state` 并列的位置，见下例；此时还没有取得模型判断 |
| 截图报 `Element not found: --path` | 当前 agent-browser 将不支持的 `--path` 当成元素选择器 | 使用位置参数 `agent-browser --session <会话名> screenshot ./page.png --json`，当前 CLI 选项以 `screenshot --help` 为准 |

`jev_check` 的正确参数形状（`state` 放事实，`propositions` 放要核对的结论）：

```json
{
  "state": {
    "evidence": ["任务状态可读取；三个写入工具均返回同一校验错误"],
    "unknown": ["尚未定位具体记录和字段"]
  },
  "propositions": {
    "write_path_blocked": "证据表明多个工具的写入路径受阻",
    "root_cause_proven": "现有证据已证明具体哪个字段触发校验错误"
  }
}
```

`swarm_status` 显示需求、合同、流程版本及规划审核状态。调用失败不表示门禁已通过；先区分参数错误、认证拒绝和持久化故障，再选择恢复动作。
