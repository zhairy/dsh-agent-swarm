# 使用

## 天枢怎么工作

在「天枢」会话里，你只需用自然语言描述目标和验收条件。天枢按固定协议推进：

1. **建立任务卡**（`swarm_task_card`）：记录目标、验收标准、范围、风险标志和性能预算（不知道的写「待测」）。规则引擎据此给出**硬门槛**；衡鉴（Jev）在规则未覆盖的部分补充门禁，**只能增加、不能减少**。
2. **委派专家**（`swarm_delegate`）：把自包含的子任务交给某个角色。插件负责选择模型路由、限制工具权限、校验结构化交付，并把证据写入账本。
3. **查看状态**（`swarm_status`）：查看每个门禁是否已由证据满足，以及各委派的路由、耗时和告警。
4. **验收**（`swarm_accept`）：`accept` 时逐项核对门禁证据，缺一项就返回 `blocked` 和缺失清单；`reject` 进入修复轮次，最多 2 轮；`incomplete` 如实记录未完成的部分。

不同风险的任务会拉起不同规模的角色组合：

| 任务 | 典型角色组合 |
|---|---|
| 微小低风险改动 | 疾风 + 复核 |
| 一般代码任务 | 铸剑或疾风 + 复核 |
| 架构、并发、算法 | 另加御史 |
| 交易/量化核心 | 另加算衡研算与验算、差分/性质测试 |

另外三个角色按需出场：行舟只在有明确执行步骤时，观象只在有图片时，妙笔只在需要文案时。

## 门禁（硬门槛）

| 门禁 | 什么时候必需 | 什么证据算满足 |
|---|---|---|
| `G_VERIFY` 复核 | 任务涉及代码改动，或本任务中出现过铸剑/疾风的委派 | 最后一次编辑**之后开始**的复核，判定为 `pass`，且至少一条命令带退出码 |
| `G_REVIEW` 御史 | 跨模块架构、共享状态并发、算法改动、安全、资金逻辑、时间序列/回测；或 Jev 判定变化较大 | 最后一次编辑之后的御史审查；其中每条 critical/high 发现都在 `swarm_accept` 的 `findingResolutions` 里写明了处理结果 |
| `G_MATH_RESEARCH` 算衡·研算 | 改变算法语义；或 Jev 判定为 research | 研算结果包含不变量和复杂度 |
| `G_MATH_VERIFY` 算衡·验算 | 资金、时间序列/回测、状态机、数值精度、共享状态并发；或 Jev 升级 | 有验算结果；与研算模型家族相同时会标注「独立性未实现」 |
| `G_DIFF_TEST` | 资金或时间序列类的算法改动 | 复核结果中有通过的 `differential` 或 `property` 类命令 |
| `G_BENCH` | 声明了性能预算（「待测」不算）；或 Jev 判定需要基准测试 | 复核结果中有通过、且带数值摘要的 `benchmark` 类命令 |
| `G_VISION` | 任务包含截图、设计稿或视觉产物 | 观象完成了观察（不是 blocked） |

两个模型都认为没问题，不算通过。复核的结论必须来自真实运行的命令和退出码。

## 示例

> 检查我的 FastAPI WebSocket 模块是否有并发问题，尽量保持现有结构。修复后运行现有测试并说明剩余风险。

天枢会建立任务卡（标志：代码改动、共享状态并发）。门禁包括复核、御史和算衡·验算。预期流程：探微或枢机定位边界 → 铸剑修改 → 复核运行测试 → 御史独立审查 → 验收。最终回复会列出改动文件、测试证据和未解决项。

> 请先让「观象」分析这张图中的 K 线布局，再让「妙笔」提出中文按钮及错误提示文案，最后由「铸剑」实现；请「行舟」构建、「复核」执行测试，最后让「观象」对照新截图检查视觉结果。

截图需要保存在工作区里，例如 `shots/target.png`，天枢把路径通过 `image_paths` 交给观象。如果路由链上没有支持图片的模型，观象会返回 `vision-unsupported`，**不会**退化成纯文本推测。

> 修复笔的增量更新和性能

量化核心任务会触发整套门禁：算衡研算定义不变量 → 铸剑实现 → 复核运行差分测试和基准 → 算衡验算与御史独立审查。

## 直接使用角色预设

新建会话时可以直接选择角色预设：

- **算衡**：只做数学研讨；
- **妙笔**：只写文案；
- **复核**：只运行检查并解释失败，不修改业务代码。

在这些预设中，只读类角色调用 `write`/`edit` 会被守卫拒绝，也没有 shell。

## 账本

每个会话一个 JSONL 文件，路径为 `%USERPROFILE%\.dsh\share\dsh-agent-swarm\ledger\<会话 ID>.jsonl`。事件类型包括：

- `task/card`
- `delegation/queued` / `running` / `completed` / `failed` / `blocked`
- `route/skipped`、`route/fallback`
- `jev/call`、`native/call`、`accept/decision`

写入前会脱敏，不记录密钥、完整 prompt 或源码。`swarm_status` 会给出当前会话账本的路径。

## 覆盖路由与策略

在 profile 的 `cordis.patch.yml`（例如 `%USERPROFILE%\.dsh\profiles\swarm\cordis.patch.yml`）末尾追加对 `swarm-core` 行的覆盖，然后重启 `dsh`。可参考 [config/roles.example.yaml](../config/roles.example.yaml) 和 [config/policy.example.yaml](../config/policy.example.yaml)。

注意：

- 覆盖会**整体替换** swarm-core 的 config，没写的字段会恢复默认值。
- DSH 0.1.7-alpha.2 的 Web 端不会自动为插件生成配置表单，所以本插件首版没有图形化配置页。配置字段都标记为 volatile，DSH 的配置编辑接口可以修改它们，每次读取都取最新值。

## 常见阻塞

| 返回 | 含义 | 处理 |
|---|---|---|
| `vision-unsupported` | 观象的路由链上没有支持图片输入的可用模型 | 在「设置 → 模型」启用支持图片的模型（例如 qwen3.8-max），或覆盖 `guan_xiang` 的链 |
| `no-usable-route` | 链上的 provider 都没有配置或无法解析 | 运行 `npm run doctor`，补齐 provider 与 key |
| `native-unavailable` | 请求了 codex/claude，但对应官方 bundle 未安装 | 按安装文档第 7 步安装；插件会自动退回 API 路由 |
| `native-budget` | 本会话的原生后端调用次数已用完 | 调大 `native.maxCallsPerSession`，或直接用 API 路由 |
| `rules+jev-fallback` | Jev 超时、限流或未配置 key | 这是保守结果：涉及算法改动时会强制验算与审查 |
| 预算上限 | 任务委派数或单角色调用次数达到上限 | 拆分任务，或调整 `budgets` |
