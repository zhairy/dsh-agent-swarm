# DSH Agent Swarm 3.3.1 OpenAI 元数据与输出上限修复

## 1. 背景

DSH 0.2.1-rc.5 使用的 pi-ai 1.5.0 中，官方 `openai` Responses 目录把多个 GPT-6 模型记录为 `contextWindow=272000`。OpenAI 官方文档对 GPT-6 Astra、GPT-6 Sol、GPT-6.1 Sol、GPT-6 Luna 和 GPT-6.1 Terra 给出的规格均为 1,050,000 context、922,000 maximum input 和 128,000 maximum output。272K 只是长上下文计价分界，不是上下文容量。

真实历史会话显示，`openai/gpt-6.1-sol` 请求被 DSH 记录为 `contextWindow=272000`，同时上下文已达约 368K tokens。该请求随后以 `incomplete/max_output_tokens` 结束。上下文容量与输出容量互相独立，且 reasoning tokens 与可见输出共享 `max_output_tokens`。

## 2. 目标

- 修正 Swarm 路由准入对已知 OpenAI API 模型的上下文判断，避免把官方 1.05M 模型当成 272K。
- 保持 OpenAI Codex/ChatGPT Work 与第三方网关的 provider 边界，不把所有 `gpt-6*` 路由无条件改成 1.05M。
- 提供只读 `doctor` 检查和安全、可回滚的 profile 元数据修复脚本。
- 对 `max-tokens` 给出明确说明：1M context 不等于 1M output，推理 token 也占用 128K 输出预算。
- 发布 `3.3.1`，不要求升级 DSH 本体。

## 3. 修改范围

- 新增权威 OpenAI API 模型元数据表和查询函数。
- `context-admission.ts` 仅对 provider `openai` 的已知模型使用权威容量；请求方显式设置的输出上限继续原样进入实际请求，准入侧仍按较保守的默认输出预算预留空间。
- `doctor` 检测当前 profile 的直接 OpenAI 模型目录是否仍为错误的 272K。
- 新增 `repair-openai-metadata.mjs`：默认只检查，`--apply` 才备份并原子修改 profile 的 `cordis.patch.yml`。
- 失败提示区分输出截断与上下文超限。
- 更新版本、文档、发布说明和回归测试。

## 4. 风险与边界

- Codex/ChatGPT Work 订阅链路的默认上下文可能低于 API；不能把 API 的 1.05M 无条件覆盖到 `codex`、`openai-codex` 或第三方兼容网关。
- 128K 是模型输出硬上限，不能通过插件扩大。超过时必须分段、请求继续、降低 reasoning effort、减少输入或输出形式。
- 本次不修改 DSH 核心包和 pi-ai 安装目录；profile 修复由显式命令执行，并保留备份。
- 不使用接近 1M token 的真实请求做成本型压力测试；以运行时目录、真实短调用和确定性单元测试验证补丁。

## 5. 验证方式

- 368K tokens 的直接 OpenAI 路由应通过准入，并以 1.05M context 和 128K output 保留安全余量。
- 相同数值在 `codex` 等非直接 API provider 上继续使用宿主元数据，不被无条件放大。
- profile 修复脚本在 `--check` 时发现 272K，在 `--apply` 后改为 1.05M，并生成备份。
- 类型检查、全量 Vitest、Host 集成、安全审计、发布闭包、真机重启和 OpenAI 短调用通过。

## 6. 回滚方案

恢复修复脚本生成的 `cordis.patch.yml` 备份，重载 DSH，并恢复上一版 `dsh-agent-swarm` bundle。不得反向覆盖 Swarm 状态或旧会话。
